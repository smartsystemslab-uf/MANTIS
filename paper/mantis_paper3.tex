\begin{abstract}
MANTIS (Modular Agent Network Testbed for Instrumentation and Security) is a configuration-driven security, compliance, and observability testbed built directly on a real, unmodified banking multi-agent system. This paper consolidates the system's two prior papers -- the original testbed~\cite{mantis_paper1} and its first set of post-paper extensions~\cite{mantis_paper2} -- into a single, complete account of MANTIS as it stands today, and contributes one further extension neither prior paper covers: a toggleable Anti-Money Laundering (AML) office, ported from the legacy codebase MANTIS's banking agents were originally extracted from~\cite{citi_p3_repo}. The complete system instruments an otherwise-unmodified front/mid/back-office banking agent system at five fixed control points through a hook bus, where an attack, failure, or defense plugin declares its target entirely in YAML and is dispatched through the identical interface regardless of kind. On top of this base, MANTIS now ships six security-mechanism defenses that close every attack in its catalog, a real toggleable integration of the independently-developed Zero Trust Backplane project -- migrated in this revision to that project's own generic architecture rewrite -- four additional observability exporters, three additional banking workloads plus a second institution profile, a minimal schema-driven browser UI, and an extended scenario library of 19 measured baselines and 26 attack/fault variants. We report live-verification evidence for every capability in the system -- checked against its actual emitted trace or persisted database state, never a clean exit code alone -- and show that this discipline catches real defects an otherwise-passing offline test suite misses entirely: live runs surfaced and let us fix two integration defects in the new AML office and one in the migrated Zero Trust integration, none of which an offline suite of 900 passing tests (879 with neither optional dependency installed, zero failures in every combination) caught on its own. Every live capability reported here is reproducible from a committed configuration file against the real backend and a real model. Code, evidence, and configurations: \url{https://github.com/smartsystemslab-uf/MANTIS}.
\end{abstract}

\section{Introduction}

Large language model (LLM) agents are moving from single-turn assistants into orchestrated multi-agent systems that carry out multi-step business processes, and banking is a natural early target: recent work proposes multi-agent frameworks for financial anomaly detection \cite{anomaly_detection_finance} and credit assessment \cite{masca_credit}, each decomposing a task across specialized agents the way a bank already organizes front-, mid-, and back-office work. That same decomposition is also where new security risk enters -- inter-agent communication is an exploitable surface in its own right \cite{prompt_infection, aitm_communication_attacks}, and a broad survey of agentic security concludes most defenses evaluated in isolation can be bypassed by an adaptive attacker \cite{agentic_security_survey, security_considerations_mas}. No widely available testbed previously let a researcher take a realistic, domain-specific multi-agent system and run controlled adversarial experiments against it without either reimplementing the orchestration framework or editing the business logic under test \cite{redagentbench}.

This paper is a consolidation, not a third independent contribution. The original MANTIS paper~\cite{mantis_paper1} built the hook bus, the banking runtime adapter, five attack and failure configurations, a seven-dimension evaluator, and a benchmarking suite -- and named five extensions deliberately deferred to future work. A second paper~\cite{mantis_paper2} implemented all five: additional observability exporters, security-mechanism (defense) plugins, additional banking workloads and a second institution profile, a minimal schema-driven UI, and -- after a team decision reversed an earlier exclusion -- a real, toggleable integration of the independently-developed Zero Trust Backplane project~\cite{ztb_repo}. Both papers' own artifacts (code, tests, and recorded evidence) remain frozen and unmodified; this paper neither edits nor supersedes them, it reports the complete system built on top of them, plus two further developments neither of them covers: a new AML office extension, and tracking the Zero Trust Backplane project's own subsequent architecture rewrite.

This paper's contributions comprise three parts:
\begin{itemize}
\item We consolidate two prior papers -- the original five-control-point testbed and its five post-paper extensions -- into a single, complete, reproducible account of MANTIS as it exists today, including migrating the Zero Trust Backplane integration to that independent project's own v1.0.1 generic-architecture rewrite after confirming the originally integrated release had been deleted upstream.
\item We port a fourth banking domain, an AML (Anti-Money Laundering) office, from the legacy codebase MANTIS's banking agents were extracted from, preserving its detection logic unchanged and gating it behind a toggle that leaves every pre-existing configuration's root agent byte-identical when absent.
\item We report live-verification evidence -- checked against the system's actual emitted trace or persisted database state, not a clean exit code or a passing unit test in isolation -- for every capability in the system, and show this discipline catches real defects an offline test suite alone misses: two in the new AML office and one in the migrated Zero Trust integration, each found only once the corresponding capability was actually run live.
\end{itemize}

The remainder of this paper is organized as follows. Section~\ref{sec:background} summarizes the motivation and related work established in~\cite{mantis_paper1}. Section~\ref{sec:design} describes the complete current system design -- architecture, the attack/defense plugin libraries, the Zero Trust and AML extensions, and the additional workloads -- without embedding experimental results in it. Section~\ref{sec:setup} describes the experimental setup shared by every live result in this paper. Section~\ref{sec:experiments} reports those results: attack and defense effectiveness, Zero Trust and AML live verification (including the real defects live verification found and fixed), additional-workload and UI evidence, the offline test suite, and a summary of findings. Section~\ref{sec:conclusion} concludes, and a dedicated Limitations section states this paper's scope honestly rather than folding it into the results.

\section{Background and Motivation}
\label{sec:background}

Multi-agent decomposition is a natural fit for banking because the workloads are already organized around specialized roles -- monitoring, investigation, compliance sign-off, decision -- and prior work demonstrates this pattern being actively explored in finance \cite{anomaly_detection_finance, masca_credit}. Three properties of multi-agent LLM systems create risk a single-agent deployment does not have: agents ingest content produced by \emph{other agents}, not only end users, so a compromised or spoofed agent's output can influence every downstream consumer \cite{prompt_infection}; routing and hand-off decisions are themselves attack surfaces, since an adversary who can intercept or relabel an inter-agent message can redirect a request to the wrong specialist or skip a required review step \cite{aitm_communication_attacks}; and tool invocation -- the mechanism by which an agent actually moves money or posts a ledger entry -- can be mutated in flight, a materially different threat than a model simply answering incorrectly. General red-teaming benchmarks for LLM agents \cite{redagentbench} provide reusable attack scaffolding but evaluate against synthetic or generic tasks rather than an existing, production-shaped business workflow, and are not designed around the constraint that the business logic under test must remain completely unmodified -- a constraint that matters because a testbed requiring edits to the fraud-review agent's own logic to add an experiment cannot be trusted to measure that agent's real behavior. Zero Trust architecture -- never trusting a request implicitly, mediating every action through explicit policy \cite{nist_zero_trust}, increasingly proposed specifically for agentic AI systems \cite{zero_trust_agentic_identity} -- is the complementary governance layer Section~\ref{sec:ztdesign} reports as a real, toggleable integration rather than the deliberately-deferred direction the first paper treated it as.

\section{System Design}
\label{sec:design}

This section describes what MANTIS is and how each extension works. It deliberately contains no live-verification results -- those, and the evidence behind every claim made here, are reported together in Section~\ref{sec:experiments}.

\subsection{Architecture and Hook Bus}
\label{sec:arch}

Figure~\ref{fig:architecture} shows the complete MANTIS pipeline as it stands today. An experiment is declared entirely in a YAML configuration; an orchestrator establishes a run identifier, seed, and lifecycle, then drives the banking workflow through a hook bus exposing five fixed control points -- input, agent, interaction, tool, and output. Each dispatch carries a typed context (run id, trace id, workflow id, stage, source, target, payload, metadata) to every registered plugin whose declared stages match; a plugin returns \emph{continue}, \emph{mutate}, \emph{skip}, \emph{deny}, \emph{delay}, or \emph{error}, and a mutation threads correctly to the next plugin in the same dispatch while the fact that one occurred is recorded in context metadata, so a plugin dispatched later in the same chain -- the observability plugin, by design, so it can observe every attack's effect -- can distinguish a genuinely adversarial event from an ordinary one.

Beneath the hook bus, a banking runtime adapter presents one stable interface (\texttt{inventory()}, \texttt{workflows()}, \texttt{build()}) over four domains: front office (transaction monitoring, fraud detection, compliance, customer service, dispute filing), mid office (operations planning, representative assist, loan pre-approval), back office (end-of-day reconciliation, settlement, SAR/exception escalation), and -- new in this paper -- AML office (structuring/mule-ring/identity-document investigation and SAR drafting, Section~\ref{sec:aml}). The live inventory (\texttt{mantis --inventory}), introspected from the tool modules and agent registry rather than maintained as a hand-authored list, reports all four domains unconditionally: 38 agents and 34 tools with the AML office registered, of which the AML office's own toggle (Section~\ref{sec:aml}) adds 4 agents and 7 tools over the 34-agent, 27-tool front/mid/back-office tree every configuration used before this paper. The AML toggle governs only whether a \emph{given run}'s actual agent tree instantiates those agents, not whether the inventory can discover or validate against them.

Every hook dispatch is mapped to one of seven typed event families (experiment, workflow, agent, interaction, tool, security, evaluation), exported as portable JSONL, OpenTelemetry spans, and an MLflow run sharing the same configuration hash and seed, with four additional OTLP-compatible exporters (Jaeger, Grafana Tempo, Phoenix, Langfuse) added as one-line configuration changes that fail silently rather than aborting a run when no collector is reachable. An automated evaluator reads a run's trace and reports trace completeness, tool-use correctness, workflow outcome, hook-point coverage, banking-domain coverage, artifact integrity, and attack ground truth -- the last distinguishing a plugin that merely fired from one whose effect is corroborated against the configuration's own expected-tools/terminal-state baseline (this evaluator is what every result in Section~\ref{sec:experiments} is scored by). Every run manifest records a SHA-256 configuration hash, the seed, the Python interpreter and dependency versions, the source commit, and whether the run used a mock or live model and which model served it, so a reported result always traces back to the exact code, environment, and model that produced it.

\subsection{Attack and Failure Plugin Library}
\label{sec:attacks}

Five attack and failure configurations span all three always-on domains, registered through the identical plugin interface. Prompt injection and message spoofing both intercept the interaction control point (an agent's outgoing call to the underlying model). Route confusion intercepts a routing tool call and forces execution to a different downstream agent than the one the orchestration logic selected. Tool-parameter mutation intercepts a tool call directly and rewrites its arguments, shipped against both a front-office funds transfer and a back-office ledger post. A reliability-failure family (delay, timeout, malformed result) emits an \texttt{ANOMALY} security event rather than \texttt{ATTACK\_INJECTED}, so an evaluator separates a security-caused anomaly from a routine fault by event type rather than inference. The extended scenario library (Section~\ref{sec:workloads}) widens this catalog to 26 attack and fault variants under the identical interface, without changing the architecture.

\subsection{Security-Mechanism Defenses}
\label{sec:defenses-design}

Six security-mechanism plugins cover every category a defense-in-depth testbed should, each registered through the identical \texttt{apply(ctx) -> HookResult} contract an attack plugin uses and classified in the trace as a distinct \texttt{POLICY\_EVENT} rather than misclassified as an attack. \textbf{\texttt{AmountLimitGuardrailPlugin}} denies a tool call whose declared amount exceeds a configured limit. \textbf{\texttt{RiskAwareRoutingGuardPlugin}} independently re-fetches a transaction's real risk score from the banking backend rather than trusting the router's own decision, with an optional \texttt{redirect\_to} recovery mode that routes to the compliant path instead of merely blocking. \textbf{\texttt{ResponseRedactionPlugin}} masks account-number-shaped tokens at the output control point. \textbf{\texttt{BatchIntegrityGuardPlugin}} independently re-checks a target batch's real expected-vs-posted totals before an end-of-day ledger update is allowed to proceed. \textbf{\texttt{RateLimitGuardrailPlugin}} caps calls per run, time window, or argument value. \textbf{\texttt{ActionIsolationPlugin}} refuses tools with a chosen side effect regardless of caller. Section~\ref{sec:experiments}.A reports each plugin's live-verified effect against the attack it was designed to close.

\subsection{Zero Trust Backplane Integration}
\label{sec:ztdesign}

MANTIS integrates the real, independently-developed \texttt{Citi\_P3\_Zero\_Trust\_Backplane} project~\cite{ztb_repo} -- not a reimplementation -- as a toggleable extension, pinned to its \texttt{v1.0.1} release via a git submodule rather than an unpinned checkout, for the same reproducibility reason every other dependency here is pinned. (This revision migrates the integration to that project's own generic-architecture rewrite; Section~\ref{sec:experiments}.B reports why, and a real defect that migration's own live verification found.) Unlike every other defense in this paper, it is not a \texttt{PolicyPlugin} dispatched through MANTIS's own hook bus: the real project's own generic \texttt{ZeroTrustPlugin} is an ADK plugin, registered directly on MANTIS's ADK \texttt{App} immediately after \texttt{MantisHookPlugin}, so every attack, policy, and observability dispatch through the hook bus still happens unconditionally before Zero Trust gets a final, independent say over whether the real tool call proceeds. A stock install never imports it, checked the same way every other optional dependency in this testbed is. A dedicated \texttt{zero\_trust: \{enabled: true\}} block (or the equivalent checkbox in the minimal UI, Figure~\ref{fig:ui-editor}) turns it on or off per run; MANTIS's own contribution is a profile pointing the real project's own scanner at MANTIS's actual ADK application factory, so the signed protection bundle it builds comes from importing and introspecting MANTIS's live agent/tool graph directly, not from a hand-written policy file. A design property worth stating plainly rather than glossing over: the real scanner's placements are per-agent -- which agent's own declared tools include a given call -- not per-domain, which is \emph{stricter} than this integration's original ``agent may act on a tool in its own domain'' claim: a same-domain agent that was never wired to a given tool is denied too, not only a cross-domain one. Because the AML office (Section~\ref{sec:aml}) adds a fourth sub-agent that changes the live graph's fingerprint, a second bundle is built and committed against an AML-enabled application factory; the plugin builder's own flag selects the bundle matching a run's actual graph, and loading the wrong pairing raises the real project's own staleness check rather than silently enforcing against a mismatched graph.

\subsection{The AML Office: Porting Anti-Money Laundering from Citi\_P3}
\label{sec:aml}

MANTIS's banking agents were extracted from a larger legacy monorepo, \texttt{Citi\_P3}~\cite{citi_p3_repo}, during the original migration documented in \texttt{MIGRATION.md}. That legacy codebase's \texttt{citi\_banking\_adk} package included a working AML investigation office -- an investigator agent, a SAR drafting agent, and four real detection functions -- that was never carried over when the rest of the codebase was translated into MANTIS's modular, hook-bus-instrumented architecture. This section reports that port: the detection logic is adapted, not reinvented, with the mathematics and control flow of every detection function unchanged from the source; MANTIS-side work is confined to the toggle mechanism, the agent-tree wiring, and the data-access layer the ported functions call into.

Four detection functions are ported with their logic unchanged. \textbf{Structuring detection} (\texttt{detect\_structuring}) evaluates a sliding window over a customer's inbound deposit-like transactions, accumulating a rolling total and reporting a hit whenever that total, within a configurable window (default 7 days), meets or exceeds a configurable threshold (default \$10{,}000); a genuine hit creates a persisted AML alert and, optionally, a manual review case. \textbf{Threshold-anomaly checking} (\texttt{check\_threshold\_anomaly}) flags a transaction exceeding 5$\times$ a customer's baseline peak transfer amount. \textbf{Mule-ring detection} (\texttt{find\_mule\_rings\_for\_customer}) builds a directed graph from a customer's own transaction flows and reports closed loops via graph cycle detection, scoped -- as in the source -- to ring segments where the customer's own accounts appear as an endpoint. \textbf{Identity-document verification} (\texttt{verify\_identity\_document}) scores a submitted name (Unicode-normalized, case-folded, Levenshtein similarity), date of birth (exact calendar-date match), and ID number (exact string match) against reference values, weighted 0.30/0.30/0.40, returning a bounded, deterministic confidence score. Separately, an alert-lifecycle state machine (\texttt{open} $\rightarrow$ \texttt{in-investigation} $\rightarrow$ \texttt{cleared}/\texttt{escalated-to-sar}) is ported from the legacy codebase's standalone backend service into \texttt{BankingRepository}, the same SQLite-backed data-access layer every other banking tool already uses, with three new tool wrappers (\texttt{get\_aml\_alert}, \texttt{list\_aml\_alerts}, \texttt{transition\_aml\_alert\_status}) giving an agent a real path to use it.

The AML office follows the same two-layer toggle discipline Section~\ref{sec:ztdesign} established for Zero Trust, adapted to a domain rather than a policy plugin. \textbf{Per-run}: a dedicated \texttt{aml\_office: \{enabled: true\}} configuration block (mirroring \texttt{zero\_trust:}'s shape) controls whether the root agent's \texttt{sub\_agents} list includes the AML office router; every configuration without that block produces a root agent whose \texttt{sub\_agents}, instruction, and description are byte-identical to before this domain existed, verified directly by a regression test constructing the agent tree both ways and diffing it. \textbf{Packaging}: mule-ring detection's graph-cycle dependency (\texttt{networkx}) is an optional extra (\texttt{pip install -e ".[aml]"}), imported lazily inside the one function that needs it, so every other AML tool, and \texttt{mantis --inventory}/\texttt{--validate}, work in a stock install.

\subsection{Additional Workloads, Minimal UI, and Scenario Library}
\label{sec:workloads}

Three additional banking workloads, each backed by real persisted records rather than a new prompt into an existing process: dispute filing (front office), SAR/exception escalation (back office), and loan pre-approval (mid office), the last computing a real, deterministic decision from seeded account data rather than an LLM opinion. A second institution profile (\texttt{regional\_credit\_union}) reuses every agent, tool, and workflow unchanged against an isolated database and a genuinely stricter policy threshold (10\% of balance versus 25\%), selected by a runtime configuration field. A minimal, schema-driven browser UI (\texttt{mantis --ui}, Figures~\ref{fig:ui-editor}--\ref{fig:ui-eval}) provides an experiment editor and trace viewer whose every mutating action -- validate, run, campaign -- shells out to the identical \texttt{mantis} CLI subprocess a terminal user would invoke; dedicated toggle fieldsets for Zero Trust and the AML office sit alongside the generic attack/policy dropdowns. An extended scenario library ships 19 measured no-attack baselines and 26 attack/fault variants, and a from-scratch walkthrough adding a new attack plugin in about fifteen lines. Five starter campaigns -- the original four~\cite{mantis_paper2} plus a fifth for this paper's own AML office -- each a single \texttt{mantis --campaign} command producing a consolidated report.

\section{Experimental Setup}
\label{sec:setup}

Every live result in Section~\ref{sec:experiments} is produced the same way. \textbf{Model.} All live runs use \texttt{gpt-oss-20b} served via UF Navigator (\texttt{https://api.ai.it.ufl.edu}); the run manifest records the serving model and endpoint host for every run, never the credential, so a reported result always traces back to the exact model that produced it. Results on a different model would need separate re-runs; none are reported here. \textbf{Scoring.} Every reported result is read from the automated evaluator described in Section~\ref{sec:arch} (\texttt{mantis --evaluate}), applied to the real emitted trace of a real run -- never inferred from a plugin having fired, an exit code, or a passing unit test in isolation. \texttt{tool\_use\_correctness} compares the tools a run actually called against a configuration's own \texttt{expected\_tools}/\texttt{forbidden\_tools} baseline; \texttt{workflow\_outcome} compares the real terminal state reached against the configuration's \texttt{expected\_terminal\_state}; attack ground truth corroborates that an attack's effect is observable in the real trace or persisted database state, not merely that the plugin dispatched. \textbf{Repetition.} Attack, defense, and workload live-verification claims are repeated-trial results (5 trials per configuration unless stated otherwise); AML and Zero Trust verification claims are each a single, officially scored run per scenario from a committed configuration file, reproducible by re-running that same file. \textbf{Environment.} Every run manifest records a SHA-256 configuration hash, the seed, the Python interpreter and dependency versions, and the source commit (Section~\ref{sec:arch}); the offline test suite (Section~\ref{sec:experiments}.E) runs against two independent dependency configurations (\texttt{zero\_trust} and \texttt{aml} installed or not) to confirm every optional extension is genuinely opt-in.

\subsection{Attack and Defense Effectiveness}
\label{sec:exp-attacks}

Table~\ref{tab:attacks} reports live, repeated-trial outcomes for the five base attack and failure configurations (Section~\ref{sec:attacks}) against the undefended system. Route confusion is unambiguous and total: fired and produced its ground-truth effect in every trial, with the router's real transfer diverted to the chatbot workflow and compliance never reached. Tool mutation (front office) genuinely reached and altered the real call every trial, with the banking backend's own destination-account validation independently catching it every time -- a defense-in-depth result, not a plugin failure. Message spoofing, prompt injection, and the malformed-failure control each show a genuine, verified mutation reaching the real model, with the model consistently declining to act on it. The extended scenario library (Section~\ref{sec:workloads}) widens this evidence to 123 scored live trials across 26 attack and fault variants without changing the architecture (Figure~\ref{fig:library-chart}).

\textbf{Finding: live verification caught a defect the unit suite also missed.} The first version of this migration built the protection bundle against the application factory called with no MCP session. This is the second, independent instance in this paper of live verification catching what an offline-only check missed (Section~\ref{sec:exp-aml} reports the first) -- neither defect involved incorrect logic in isolation; both were properties of how the system is actually wired together at run time.

\subsection{AML Office: Live Verification and Two Real Defects Found}
\label{sec:exp-aml}

Five scenarios exercise the AML office end to end against the live backend and a real model: a structuring-detection positive case (three seeded inbound wires from one counterparty summing to \$12{,}000 within seven days, past the \$10{,}000 threshold), a structuring negative control, a mule-ring negative control, an identity-verification case, and an alert-triage case against a seeded reference alert. The first live pass of all five surfaced two real integration defects, neither caught by the unit test suite because both are properties of the \emph{live agent tree}, not of the ported functions in isolation.

\textbf{Routing gap.} The identity-verification scenario was misrouted to \texttt{front\_office\_router} instead of \texttt{aml\_office\_router}: the root agent's routing instruction mentioned ``AML investigation, suspicious activity, and SAR drafting'' but not identity verification by name, and a plausible-sounding KYC-flavored prompt was reasonably routed to the front office instead, where it called \texttt{get\_customer\_context} with the submitted ID number in place of a customer id and produced a nonsensical result. The fix was wording, not logic: the root agent's and the AML router's instructions now explicitly name identity-document verification and alert triage as AML-office tasks.

\textbf{Unreachable capability.} The alert-triage scenario asked to transition a seeded alert's status; \texttt{transition\_aml\_alert\_status} existed, was correctly implemented, and was unit-tested directly as a function -- but no agent in the built tree had it, or its sibling read tools, on its toolset at all. The three alert-lifecycle tools were wired into the existing \texttt{aml\_investigator} agent's toolset, the single tool-using agent in this domain, and its instruction extended to describe the triage capability.

Both fixes were verified live after correction: the identity-verification scenario now routes correctly to \texttt{aml\_office\_router} $\rightarrow$ \texttt{aml\_investigation\_workflow}, calls \texttt{verify\_identity\_document} with the exact submitted/reference values from the prompt, and reports 100\% match confidence. The alert-triage scenario now calls \texttt{transition\_aml\_alert\_status}, and we confirmed the effect directly against the database rather than trusting the model's own report: reading the alert back afterward shows its status genuinely changed from \texttt{open} to \texttt{in-investigation}. All five scenarios were then run officially from committed configuration files (\texttt{configs/extensions/aml\_office\_*\_demo.yaml}) and scored by \texttt{mantis --evaluate}: \texttt{tool\_use\_correctness} 1.0 and \texttt{workflow\_outcome} 1.0 (\texttt{completed}) for every one of the five, with zero missing expected tools and zero forbidden tools used. \subsection{Offline Test Suite}
\label{sec:exp-tests}

The offline test suite -- unit and contract tests, a parametrized consistency suite over every shipped configuration and scenario, and regression guards for every toggleable extension -- stands at 879 passing tests with neither optional dependency (\texttt{zero\_trust}, \texttt{aml}) installed (205 more skipped by design without a live backend or model), 900 passing with both installed (190 skipped), zero failures in every combination. This paper's own AML office extension adds 53 of those tests (repository-layer, detection-function, toggle, and drift-regression coverage) on top of the base established by~\cite{mantis_paper1} and the fourteen further categories added by~\cite{mantis_paper2}. The Zero Trust migration's own regression guards include deliberately building the plugin against a mismatched agent graph and confirming the real project's own check rejects it (Section~\ref{sec:exp-zt}).

\subsection{Summary of Findings}
\label{sec:exp-summary}

\textbf{Live verification catches what an offline-only check misses, twice, independently.} The AML office's two defects and the Zero Trust migration's one defect were each invisible to a passing unit test suite because each is a property of the live agent tree or the live runtime environment, not of any single function or module in isolation -- the same methodological lesson both prior papers report, now observed a third and fourth time in genuinely different subsystems.

\textbf{Defense-in-depth closes every attack in the shipped catalog.} Every attack that once succeeded undefended now has a live-verified defense (Table~\ref{tab:defenses}), with zero false positives on any paired no-attack control.

\textbf{A migrated real-world dependency can silently diverge from its own test suite's assumptions.} The Zero Trust Backplane's own generic rewrite changed what a correctly-scanned application graph looks like; because our test fixture and the original bundle-build step made the identical simplifying assumption, nothing caught the mismatch until a real run exercised it end to end.

\textbf{Per-agent enforcement is a stronger guarantee than the one originally claimed.} The real Zero Trust scanner's placements are per-agent, not per-domain -- every live result in Table~\ref{tab:zt} is consistent with the stricter claim, not only the original, looser one.

\section{Conclusion}
\label{sec:conclusion}

This paper consolidates MANTIS as a complete system: the original five-control-point testbed~\cite{mantis_paper1}, all five of its deferred extensions~\cite{mantis_paper2} including a real, toggleable Zero Trust Backplane integration now migrated to that project's own generic architecture, and -- new here -- a toggleable AML office porting real structuring, mule-ring, and identity-verification detection logic from the legacy \texttt{Citi\_P3} codebase MANTIS was originally extracted from. Every extension across all three papers shares the same discipline: a capability is reported as working only once verified against the system's actual emitted trace or persisted database state, not a clean exit code or a passing unit test in isolation. That discipline paid for itself directly in this revision, catching two real defects in the new AML office and a third in the migrated Zero Trust integration before any of the three could honestly be called working. The complete offline suite passes with zero failures across all four combinations of its two optional dependencies (879 with neither, 900 with both), and every live capability this paper reports is reproducible from a committed configuration file against the real backend and a real model.

\section*{Limitations}

\textbf{Single model evaluated.} Every live result in this paper uses one model, \texttt{gpt-oss-20b} served via UF Navigator (Section~\ref{sec:setup}); results on a different model would need separate re-runs, and we do not claim the specific numeric outcomes (e.g. an attack's ground-truth effect rate) generalize across models, only that the testbed and its evaluator are model-agnostic. \textbf{Practical, not maximal, trial counts.} Repeated-trial results use 5 trials per configuration, a practical and repeatable sample size rather than one chosen to tighten confidence bounds maximally; a larger campaign along the same already-implemented axes (Section~\ref{sec:arch}'s benchmarking suite) would narrow them further. \textbf{The AML investigator's own SAR-drafting judgment is an inherited, not introduced, limitation.} \texttt{detect\_structuring} itself is deterministic and, as Table~\ref{tab:aml-live} shows, correct; the investigator agent's own gating logic for whether to draft a SAR (risk score $\geq$ 50, or an investigation status containing ``suspicious'') is inherited unchanged from the source prompt. A live run against the positive structuring case correctly identified the pattern in its \texttt{findings} text but assigned a risk score of 7.2 -- well under the reporter's trigger threshold -- and separately populated its \texttt{case\_facts} with invented transaction amounts and dates rather than the real values the tool had just returned. We report this as a known limitation of that prompt against this specific smaller model, inherited directly from \texttt{Citi\_P3} and not something this port introduced or silently corrected. \textbf{Zero Trust's enforced scope is domain-scoped tool access, not routing.} The integration deliberately leaves \texttt{transfer\_to\_agent} unconstrained (Section~\ref{sec:ztdesign}) because MANTIS's own agent tree uses legitimate cross-domain routing as normal behavior; it does not extend to the real project's fuller workflow- and risk-aware policy model, which remains, as in~\cite{mantis_paper2}, an open direction rather than one this paper closes.
